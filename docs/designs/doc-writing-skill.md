# Design: 把文档书写规范编译成可路由的技能

Generated by /office-hours on 2026-11-01
Branch: main
Repo: MDStandardsKit
Status: APPROVED
Mode: Builder

> 分发部分已被 `docs/designs/doc-writer-plugin-distribution.md` 取代；本文中的 `.claude/skills/doc-writer` 路径与 release tarball 描述是历史记录，不是当前安装方式。

## Problem Statement

用 Agent 写 Spec 时，每次产出的结构、章节覆盖和论证顺序都不一样。评审者每次都要重新适应一份新文档，上一次踩过的坑也不会自动被避开。用户的原话：

> "我注意到让 agent 去写 spec 的时候，每次写的那个 spec 都是不太一样的，所以我需要有一个规范的方式来约束他，引导他写出一些问题的关键点。"

真正的失败点不在方案章节的文采，而在更早：背景没交代清楚、痛点没分析到位，Agent 就写出了一个结构漂亮、但解决错问题的方案。用户的评审顺序就是证据：背景 → 痛点 → 方案。

现有规范是 `framely/docs/specs` 下的 1 篇总纲加 8 篇章节指南，约 820 行 prose。Agent 读它不稳定：每次读到的重点不同，产出就不同。规范本身还在演进，但没有可执行的检查。

## What Makes This Cool

把"写文档"变成"编译文档"：长篇规范被编译成可路由的模块（route + decision guide + template + check），Agent 不再自由发挥版式，而是先回答关键问题，再按固定骨架填充。新增一种文档类型是改数据，不是改提示词。

同一套关键问题清单也为后续的审计模式提供基础：存量文档的缺口可以用同一份 checklist 标出来。技能随 MDStandardsKit 分发，写作规则与元数据闸门共用同一份 policy 目录和状态集合，不会出现"写的时候一套、检查的时候另一套"。

## Constraints

- 技能放在 MDStandardsKit，随工具分发。
- 规范搬进技能，`framely/docs/specs` 只留指针，不再保留第二份权威文本。
- v1 覆盖两类文档：技术 Spec、里程碑纪要。
- 路由必须是数据契约（注册表），不能是 `SKILL.md` 里的一段散文。
- 项目专属约定（目录、命名、状态、changelog、commit 粒度）放在 profile，核心保持通用。
- **规则不得丢失**：现有 820 行指南里的每条规范，迁移时必须能映射到 `references/`、`checks/` 或 profile 三者之一；映射表是验收物。
- **Spec 产出必须过 mdstandards**；Milestone 不走 mdstandards，走独立的 `checks/milestone.json`。
- Agent 不得编造答案；缺失的最小关键回答会阻断方案章节。
- 检查器必须可执行、可复现，不能依赖 Agent 的临场判断。
- 不引入新的运行时依赖；检查器用 Go 编写，复用已有工具链。

## Premises

1. 主要失败发生在方案之前：背景与痛点。
2. 闸门必须在起草前运行，事后检查改变不了产出方式。
3. 结构一致是必要条件，不是充分条件；验收标准是"关键问题被回答"。
4. **Spec 产出**必须过 mdstandards（YAML frontmatter、`depends_on`、可依赖状态）；Milestone 不进入 mdstandards 语料。
5. 技能随工具分发，所以核心通用、约定外置到 profile。
6. v1 用两类真实文档验证路由；更多类型通过注册表增加，不改 `SKILL.md`。

## Approaches Considered

### Approach A: 路由表写进 SKILL.md

一张表加每类一套 references/templates/checks；新增类型等于加资产加一行。Effort S/M，Risk Low。否决理由：路由是散文，不能被检查；项目约定写死；类型一多 `SKILL.md` 会膨胀。

### Approach B: 注册表 + 项目 profile（已选）

`routes.json` 声明每类的意图、必读 references、模板与校验；`SKILL.md` 只做分派；framely 的路径与约定放 `profiles/framely.yaml`。

### Approach C: 类型即独立包

`doc-types/spec/` 与 `doc-types/milestone/` 各自带 `route.md`、references、templates、checks；复制目录即新增类型。否决理由：共享的闸门问题会在包里重复，包之间容易漂移，没有统一校验。

### 会话早期被否决的方向

- **单技能只写 Spec**：范围不够，用户明确要求可写其他文档。
- **结构化决策记录 + 渲染器**：确定性最强，但引入新产物与渲染器，并给 v1 只有两条规则的 Go 工具加渲染能力，范围膨胀。

## Recommended Approach

B。核心理由：路由接口只有在它是数据契约时才可扩展；注册表能在新增类型时直接告诉你少了哪个模板或校验，`SKILL.md` 的散文做不到。

### routes.json 契约

```json
{
  "version": 1,
  "routes": {
    "spec": {
      "intent": ["写技术规格", "技术方案", "spec", "设计文档"],
      "references": ["references/_gates.md", "references/spec.md"],
      "templates": ["templates/spec/spec.md.tmpl", "templates/spec/changelog.md.tmpl"],
      "checks": ["checks/spec.json"],
      "report_check": "mdstandards -root {{root}} -policy {{policy_dir}} -phase 0 -format json",
      "block_check": "mdstandards -root {{root}} -policy {{policy_dir}} -phase 1 -baseline {{baseline}} -format json",
      "metadata": "yaml_frontmatter"
    },
    "milestone": {
      "intent": ["里程碑", "规划会议", "milestone plan"],
      "references": ["references/_gates.md", "references/milestone.md"],
      "templates": ["templates/milestone/milestone.md.tmpl"],
      "checks": ["checks/milestone.json"],
      "metadata": "body_meta_list"
    }
  }
}
```

约束：

- 每条 route 至少一个 reference、一个 template、一个 check。
- 所有路径必须存在。
- `intent` 不得为空。
- `spec` route 必须同时给出 `report_check` 与 `block_check`，且 `block_check` 必须带 `-baseline`。
- 这些约束由 `tools/doccheck -routes` 在 CI 中检查。

### 路由选择算法

1. 把用户请求转小写；ASCII 词按整词匹配，中文按子串匹配。
2. 命中一个 route 就选它。
3. 命中多个 route 时，取命中关键词最长的那条；仍然并列时，列出候选让用户选。
4. 没有任何命中时，列出已注册的 route 让用户选，不猜。
5. 选择结果写入 Gate Report 的 `route` 字段。

`tools/doccheck -routes` 带一组测试用例：重叠意图、无命中意图、空意图。

### profile 解析与根目录

- 技能接受 `--profile <name>` 参数或 `DOC_WRITER_PROFILE` 环境变量。
- 未指定时，取目标仓库根目录的 basename，查找 `profiles/<repo>.yaml`；找不到就列出可用 profile 让用户选。
- 目标根目录：当前工作目录所在的 git toplevel；不是 git 仓库时用当前目录。
- profile 里的路径相对目标根目录；技能自身的 assets 相对技能目录。
- 找不到 profile 时中止，不猜。

### profiles/framely.yaml

```yaml
name: framely
spec:
  root: docs/specs
  dir_pattern: "SPEC-{nnn}-{kebab}"
  main_file: spec.md
  changelog_file: changelog.md
  statuses: [Draft, In Review, Approved, Implemented, Superseded, Deprecated]
  dependable_statuses:
    source: policy/data/standard.json
    allowed: [Approved, Implemented]
  commit_granularity: one-spec-per-commit
milestone:
  root: docs/milestones
  file_pattern: "M{n}-plan-{nnn}.md"
checks:
  mdstandards:
    binary: "${MDSTANDARDS_BIN:-mdstandards}"
    policy_dir: "${MDSTANDARDS_POLICY_DIR}"
    standard_json: "data/standard.json"
    baseline: "${MDSTANDARDS_BASELINE:-policy/baseline.json}"
```

`dependable_statuses` 从 policy 读取，profile 只声明本仓 Spec 允许使用哪几个：`allowed` 必须同时是 `policy.dependable_statuses` 和 `profile.statuses` 的子集。`Published` 仍留在 policy 里供架构文档使用，但不进入 framely Spec 的依赖判定。

`policy_dir` 的解析顺序：`MDSTANDARDS_POLICY_DIR` 环境变量 → 技能分发包自带的 `policy/` → 目标仓库根目录的 `policy/`。framely 在 v1 不自带 policy，安装说明要求把 `MDSTANDARDS_POLICY_DIR` 指向 MDStandardsKit checkout 或解压后的分发包。`tools/doccheck -profile` 校验解析后的目录包含 `data/standard.json` 与至少一个 `.rego`，否则失败。

### 三段闸门（references/_gates.md）

`_gates.md` 只放两类文档真正共享的部分：

1. **背景**：现状是什么、触发点是什么、谁被卡住、不做的后果是什么。
2. **痛点**：失败链是什么、有没有一次具体事故或度量、现有方案为什么不够。

方案问题按文档类型分开放：Spec 的方案闸门在 `references/spec.md`，Milestone 的方案闸门在 `references/milestone.md`。不要把 Spec 的 Goals/Non-Goals/回滚问题套到里程碑纪要上。

闸门规则：

- 一次只问一个问题。
- 答案必须落到文档里，不能只停在对话里。
- **最小集**：背景四问 + 痛点失败链与一条证据。
- 最小集任一未答完，不写方案章节。用户说"跳过"时，技能记录跳过原因，但**跳过不解锁方案章节**。
- 非最小问题（例如额外的备选方案）可以记为 open question，不阻断方案章节。
- v1 不允许"带一份 brief 文件跳过逐问"；brief 可以预填答案，但每个最小项仍要用户确认。Open Question 5 在 v1 关闭。

### 阻断时的输出契约

契约按 route 展开，对两类文档同样成立：

- 闸门未通过时，技能不创建、不修改该 route 的主文件。Spec 的主文件是 `<spec.root>/<dir>/spec.md`；Milestone 的主文件是 `<milestone.root>/<file>`。
- 输出一份 Gate Report：`route`、目标文件、已回答项、缺失的最小项、下一个问题。
- 需要落盘时写到 `<route.root>/.drafts/<slug>-gate.md`。`.drafts` 是点目录，不在受管 glob 内；Spec 与 Milestone 各用自己的 root。
- 起草后仍有非最小 open question 时，写入目标文件末尾的可选附录 `## 附录 A：未决问题`；没有 deferred 项就不生成该附录。
- 技能不删除用户已有的草稿；阻断只影响本次是否继续写方案章节。

### Spec 模块（references/spec.md）

- 章节顺序：元数据 → 背景与上下文 → 目标与非目标 → 架构设计与核心方案 → 详细设计 → 非功能性需求 → 上线与迁移计划 → 替代方案与权衡 → 可选附录 A：未决问题。
- **痛点位置固定**：`## 1. 背景与上下文` 下的 `### 1.2 核心技术痛点`。评审顺序 `背景 → 痛点 → 方案` 映射到 1.1 → 1.2 → 第 3 章及以后。
- 元数据用 YAML frontmatter：`type`、`status`、`owner`、`depends_on`、`updated_at`。`title`、`reviewers`、`target_version` 作为可选字段写进正文元数据表，避免把可变字段塞进闸门。
- `depends_on` 只写真实存在的受管文档；写入前确认目标文件存在，并且状态可依赖。
- 每个 Goal 必须有验收方式；每个 Non-Goal 必须标 `本次不做` 或 `永远不做`。需要延后时写 `留待后续 Spec`，不写 `M<N>`，与里程碑无关规则保持一致。
- 替代方案必须包含 Status Quo 和至少一个被否决方案，并给出权衡矩阵。
- 上线章节必须有回滚触发条件，不能只写回滚步骤。
- 状态修改遵循现有生命周期：核心内容变更立即回退 `In Review`，大幅重写回退 `Draft`；回退期间不改生产代码。
- 修改后同步 `updated_at` 与 `changelog.md`。
- 一个 commit 只涉及一个 Spec（advisory，提醒而不阻断）。

### Milestone 模块（references/milestone.md）

- 章节顺序：标题/目标/元数据 → 核心架构与技术决策 → 里程碑范围 → 任务拆解与 Backlog → 验收标准与 DoD。
- 纪要是时间点快照，不设审批状态、不维护 changelog。
- 元数据用正文的 `基础信息 (Meta)` 列表，不走 YAML frontmatter；因此不进入 mdstandards 语料。
- 每个决策写"选了什么、为什么、带来什么约束"。
- In Scope / Out of Scope 成对出现；Out of Scope 写 `留待 M<N>` 或 `永不做`。
- Backlog 必须是一张带 Issue 列的表格，且至少有一行；"落到 Issue"指文档内的编号/链接，不要求读取外部 tracker。In Scope 与 Backlog 行的逐项对应由评审确认，`doccheck` 只检查 Issue 列存在且表格非空。
- 方案闸门是：决策带理由、范围成对、Backlog 可拆、DoD 可观测。不套用 Spec 的备选方案与回滚问题。

### 检查器 tools/doccheck

`tools/doccheck` 是确定性检查器，五种模式：

1. `doccheck -routes <routes.json> -skill <skill-dir>`：校验注册表完整性、路径存在、intent 非空、spec 有两个阶段命令。
2. `doccheck -profile <profile> -policy <policy-dir>`：校验 profile 与 policy 一致。
3. `doccheck -doc <path> -check <check.json>`：按 checklist 检查文档。
4. `doccheck -baseline <baseline.json> -report <phase1-report.json>`：校验每条 baseline entry 都能匹配当前 phase 1 的真实 finding。
5. `doccheck -placeholders <path>...`：检查模板与生成文档里的 `{{...}}`、整行 `<...>`、整行 `...` 残留。

check JSON 的 schema：

```json
{
  "version": 1,
  "items": [
    {
      "id": "pain_evidence",
      "description": "1.2 核心技术痛点 必须有失败链与一条证据",
      "selector": {"heading": "1.2 核心技术痛点"},
      "expectation": {"type": "non_empty"},
      "severity": "blocking"
    }
  ]
}
```

选择器支持三种：`heading`（可带 `regex`，匹配限定在该章节内）、`frontmatter`、`regex`（全文）。期望只支持四种：`non_empty`、`matches`、`exists`、`count_at_least`。Backlog 的 Issue 列检查用 `heading` + `regex` 实现，不引入表格解析器。输出 JSON：

```json
{"items":[{"id":"pain_evidence","status":"pass|fail","locator":"1.2","expected":"...","actual":"..."}],"summary":{"pass":0,"fail":1,"advisory":0},"exit_code":1}
```

退出码：0 全通过；1 有失败项；2 工具或解析错误。`tools/doccheck` 是普通 Go 包，放在非点目录，`go test ./...` 会跑到。

边界：`doccheck` 不做目录布局、跨文件链接解析、git 历史或语义判断。这些规则在 `references/` 里作为人工核对项，不伪装成机器检查。`count_at_least` 只用于表格行数；像 Goals 3-6 个这样的上限写在 `references/spec.md`，不进 checklist。

### 外部闸门与退出码

- 技能总是先跑 `report_check`（phase 0），把 findings、extract errors、stats 给用户看。
- **Baseline 归人管。** `policy/baseline.json` 初始为 `[]`，schema 是 mdstandards 的 `[]BaselineEntry`（`rule`、`document`、`target`）；额外字段 `rationale`、`owner`、`date` 会被 mdstandards 忽略，供人审阅。只有人能新增条目；技能与 Agent 不得写 `policy/` 或 baseline，只能只读地把它传给 `block_check`。`doccheck -baseline` 校验每条 entry 能匹配到当前 phase 1 的真实 finding，配不上的条目直接失败；CI 断言一次 skill run 前后 baseline 字节不变。extract error、零受管文档、零依赖边不能被 baseline 抑制。
- 验收只认 `block_check`（phase 1）：
  - exit 0：通过。
  - exit 1：有 findings。只有 `(rule, document, target)` 与 `policy/baseline.json` 精确匹配的 finding 可以被抑制；解释不算通过。
  - exit 2：策略加载、解析、零受管文档、零依赖边等错误。技能停止，保留草稿，报告原因，不改 policy、不改文档来绕过。
- **第一份 Spec 的路径**：必须至少有一条真实 `depends_on` 指向受管且可依赖的文档。仓库里没有这样的文档时，技能停止并请用户先建立依赖；不伪造、不用基线绕过覆盖错误。首次运行如果受管文档数为 0，phase 1 会退出 2；这是启动条件，不是缺陷，技能必须把这句话原样告诉用户。
- parse error：先修 frontmatter；extract error 不能用基线抑制。
- `mdstandards` 二进制解析顺序：`MDSTANDARDS_BIN` → `PATH` → 目标根目录的 `./mdstandards` → 在 MDStandardsKit 源码目录 `go run .`。命令从目标根目录执行。
