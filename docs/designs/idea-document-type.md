## Problem Statement

用户的原话：

> "我的工作目录下还有一个想法的项目。那个项目里面的想法是有模板的，但是他缺少一个验证结构和评估内容的方法，所以我们需要支持一个新的类型：idea。"

`~/Workspace/ideas` 是一个独立的想法记录库：一个想法一个 Markdown 文件，按年份归档。模板包含 frontmatter（`id`、`title`、`date`、`tags`、`status`）和四个固定章节（一句话描述、想法、为什么有意思、下一步）。`scripts/new` 负责创建文件、生成 8 位大写 ID、按 `YYYY/YYYY-MM-DD/<slug>.md` 命名（年份和日期都是目录，文件名只有 slug），但**没有任何校验**：空章节、ID 格式错、重复 ID、状态乱填、日期与日期目录不一致，都不会被发现。

内容层面同样没有标准。一个想法是「一句话的念头」还是「值得投入的赌注」，目前只能靠人回头看。已有的 Spec 评分卡证明了「rubric + 独立评审 + 逐字证据 + 工具复算」这条路可行，但 idea 的判断维度不同：不是文档写得好不好，而是**这个想法值不值得现在推进**。

## What Makes This Cool

把一个想法从「记录」推进到「可验证的赌注」。

结构闸门只保证机器读得懂：该有的字段和章节在、ID 唯一、日期对得上。真正有价值的是内容评分卡最重的一项——**下一步是不是一个最小、可观察、能证伪核心假设的动作**。分数不是给想法排名，而是分诊：哪些该现在试，哪些还只是好听的句子。

第二意见把它推得更远：一篇 idea 可以是一张 bet card——核心假设、最便宜的反证实验、可观察结果、kill criterion、timebox。这次不实现整套 bet card，但 rubric 会为它留位置。

另一个便宜且锋利的检查：reviewer 只看 `title` 和「一句话描述」，先猜正文在讲什么；猜不中，就是一句话描述不合格。这直接接住了模板里那句「写不出来就说明还没想清楚」。

## Constraints

- 只给 mdstandards 增加新的文档类型，不改变 spec 的现有行为、退出码和测试。
- 结构错误在记录时阻断；内容分只诊断，绝不阻止想法入库。
- ideas 的 README 明确写「写的时候不求完整，先抓住就行」。结构定义因此只包括：字段格式、章节标题存在、模板占位符已替换。空正文、`暂无`、`目前说不清，因为……` 都不算结构错误。模板占位符检查分两处：正文只扫描模板里固定的四条 HTML 注释，其他 HTML 注释忽略；frontmatter 单独检查 `id: ABCDEFGH` 哨兵。两者都算结构错误。
- 规则放在 mdstandards 的类型化 policy 里，ideas 仓库不复制规则，只声明自己是 idea 类型。
- 内容评分复用 `tools/qualitycheck` 的 rubric/审计能力；不重写评分引擎，但 findings schema 需要增加 `guess` 字段，用来记录 blind read 的猜测和依据。
- 评分产物放在独立目录，不进入受管文档，避免自评被结构闸门递归管理。
- `date` 可能被 YAML 解析成 `time.Time`；extractor 必须同时接受字符串和 `time.Time`，归一化成 `YYYY-MM-DD`，并拒绝带时间的 datetime。
- 路径必须是 `YYYY/YYYY-MM-DD/<slug>.md` 三层；额外嵌套不算合法，必须显式报错，不能静默放过。
- 先用现有五篇想法校准 rubric，再写结构闸门的 Go 代码。rubric 没信号之前，闸门没有意义。
- 不新增运行时依赖；继续用 Go 标准库 + 现有 OPA/YAML 依赖。

## Premises

1. `idea` 是第二类受管文档，规则与 spec 不同：不要求 `depends_on`；校验五个 frontmatter 字段与四个章节标题；spec 现有行为和退出码不变。
2. 记录时结构错误阻断（文件已建，agent 必须当场补齐）；内容分只诊断，不阻止入库。
3. 内容评分复用 spec 评分卡骨架：idea 专属 rubric、独立评审、逐字证据、qualitycheck 复算；最高权重给「下一步可验证」。
4. 「写不出来」允许记录：一句话描述可以写「目前说不清，因为……」；空正文和 `暂无` 也允许。只有未替换的模板注释/占位符算结构错误。
5. 规则只有一份，放在 mdstandards 的类型化 policy 里；ideas 仓库通过仓库级配置声明类型，不复制规则。评分产物放独立目录，不进受管文档。
6. 插件新增 idea 写作流程，让「记一下」自动跑完：建文件 → 填模板 → 结构闸门（同步）→ 内容评分（落盘后，不阻塞回复）→ 报告。

## Cross-Model Perspective

独立子代理冷读后的关键判断：

- **最酷的版本**：把评分卡从「这个想法好不好」改成「这个想法多快能被证明是错的」。一篇 idea 是 bet card：核心假设、最便宜的 falsifying test、可观察结果、kill criterion、timebox、revisit trigger。rubric 最高权重不是「下一步有没有动作」，而是「下一步是不是一个 ≤1 小时、能杀掉这个想法的实验」。
- **最兴奋的点**：用户要的不是「把想法写规范」，而是「把想法变成可证伪的赌注」。结构校验只是让赌注能被机器读到；真正想做的是 falsification。这也解释了为什么内容分不阻断——要的是分诊，不是审判。
- **挑战的前提**：记录时同步跑独立评审会拖垮手机上的「记一下」；空章节算结构错误会逼 agent 编内容，违反 ideas 的 CLAUDE.md。两条都已修订。
- **原型建议**：周末先不写 Go，用现有 qualitycheck 和五篇存量想法证明 rubric 有信号；有信号再做最小结构闸门。

未采纳为 v1 的部分：bet card 的完整字段、triage 状态流转、idea 图谱。它们作为 rubric 的加分项保留，不扩成新系统。

## Approaches Considered

### Approach A: 类型配置 + 专用 Rego（最小可行）

ideas 仓库根放 `.mdstandards.json`（`{"type":"idea"}`）；mdstandards 读它，从 policy 的 `document_types.idea` 取规则档案；`extract.go` 多抽 ID/Title/Date/Tags/章节信息；新增 `policy/idea.rego` 做结构规则；内容评分复用 qualitycheck。

- Effort: M　Risk: 中低
- Pros: diff 最小；spec 行为完全不动；规则仍在 policy 里；qualitycheck 一行不改。
- Cons: 类型档案仍是半特例，第三种类型要再补代码；新增仓库级配置文件约定。
- Reuses: 现有 Rego 评估、extract 流程、qualitycheck rubric/audit、插件 shim。

### Approach B: 声明式类型 schema（理想架构）

`standard.json` 升到 v2，用 `types` 声明每类的 globs、必填字段、状态枚举、必需 heading、是否有依赖图；extract 输出通用文档信封；一个通用 `schema.rego` 解释所有类型；spec 图规则只在 `graph: true` 时生效。

- Effort: L　Risk: 中
- Pros: 第三、第四种类型零 Go 改动；类型系统真正成立；规则集中。
- Cons: 要迁移 spec policy 和现有测试；Rego 复杂度上升；有过度抽象风险（仓库 D2 明确反对过早抽象）。

### Approach C: 独立 triage 工具（侧向）

不动 mdstandards 的类型系统；在 ideas 仓库加 `scripts/check`（或 `doc-writer-tool idea` 子命令），一次完成结构校验 + 内容评分；想法按「核心假设 / 最便宜的反证实验 / kill criterion」组织成 bet card。

- Effort: S–M　Risk: 低
- Pros: 最快能跑；对 spec 闸门零风险；直接交付「廉价赌注」的体验。
- Cons: 名义上没给 mdstandards 加类型；解析逻辑重复；长期维护两条路径。

## Recommended Approach

**Approach A。** 它用最小改动真正交付 `idea` 类型，spec 完全不受影响；等第三种类型出现再升到 B。

具体决策：

1. **类型声明用仓库级配置，globs 只来自 policy。** `~/Workspace/ideas/.mdstandards.json` 只写 `{"type":"idea"}`，不包含 globs；每个类型的 globs 唯一来源是 policy 档案。理由：idea 文件保持五个字段；仓库自己声明类型，而不是由调用方用 flag 声明；匹配规则不离开 policy。不采用在 frontmatter 加 `type: idea`，避免模板多一个字段。
2. **policy 增加 `document_types.idea`。** 档案包含：globs（`20*/**/*.md`，宽匹配，交给路径形状规则判断三层）、必填字段、状态枚举（萌芽/探索中/已落地/搁置）、必需二级标题（四个）、`id_pattern`（`^[A-Z]{8}$`）、`date_field`、`graph: false`。
3. **`extract.go` 增补字段。** `Document` 增加 `ID`、`Title`、`Date`、`Tags []string`、`Sections []Section`（标题、层级、正文是否为空、是否残留模板占位符），全部带 `omitempty`，且只在 idea 类型下填充；spec 的 `-dump-corpus` 输出保持逐字节不变，并加回归测试。`date` 同时接受 YAML 的字符串和 `time.Time` 两种解析结果，归一化为 `YYYY-MM-DD`；带时间的 datetime 报 extract error。`Extract` 签名改为 `Extract(root, globs, docType)`，idea 字段只在 `docType == "idea"` 时解析。章节解析复用 qualitycheck 的 fence-aware ATX 思路；不引入新依赖。
4. **新增 `policy/idea.rego`。** 规则：必填字段缺失、空/空白 title、ID 格式、ID 重复（语料级）、日期格式、日期与日期目录/年份目录不一致、状态非法、tags 类型非法、必需标题缺失、模板占位符残留、路径形状非法。日期契约是 `YYYY/YYYY-MM-DD/<slug>.md`：路径必须恰好三层，年份目录匹配 `20[0-9]{2}`，日期目录匹配 `YYYY-MM-DD`；frontmatter `date` 必须等于日期目录名，年份目录必须等于 `date` 的年份，且 `date` 必须是真实日历日期。两层或四层路径必须显式报错，不能因为 Rego 取不到段而静默放过。模板占位符检查分两处：正文扫描模板里固定的四条 HTML 注释（其他 HTML 注释忽略），frontmatter 单独检查 `id: ABCDEFGH` 哨兵。空正文、`暂无`、`目前说不清，因为……` 不报错。每条规则配一个失败 fixture，另配合法、`暂无`、`目前说不清` 的通过 fixture；日期规则补错误日期目录、错误年份目录、非法日历日期三个 fixture，路径规则补两层和四层 fixture，占位符规则补 `id: ABCDEFGH` 失败 fixture，标题规则补空和纯空白两个 fixture。
5. **规则按仓库类型作用域，覆盖断言按图类型。** `run` 的解析顺序是：先读 `.mdstandards.json` 得到 type；从 `document_types[type]` 取 globs；把 type 和 globs 传给 `Extract`；再在 `Corpus` 上写入 `DocumentType`。没有配置文件时 type=spec、globs=顶层 `governed_globs`。配置文件损坏、type 未知或含未知键一律 exit 2，不静默回退。`main.go` 只在类型不是 `spec` 时写入 `Corpus.DocumentType`（`json:"document_type,omitempty"`）；类型为 spec 时字段为空，Rego 用 `object.get(input, "document_type", "spec")` 解析有效类型。所有 `idea.rego` 规则先用它守卫，spec 图规则也只在有效类型为 `spec` 时生效；`refs.rego` 和 `status.rego` 的规则体加显式 `object.get(input, "document_type", "spec") == "spec"` 守卫。这样 spec 的 `-dump-corpus` 输出逐字节不变。`standard_version` 保持 `1`，因为这次是追加字段；真正的兼容机制是插件版本固定（binary 和 policy 同版发布）。如果未来需要旧 binary 拒绝新 schema，再升到 `2` 并更新 guard。只有 `dependable_statuses` 和零依赖边断言按 `graph: true` 生效。idea-only 仓库跑 `-phase 1` 不再因为零边退出 2；加一条 idea-only 集成测试和一条 spec dump golden。
6. **内容评分复用 qualitycheck。** 新增 `skills/idea-writer/`，包含 SKILL.md、`idea/quality/rubric.v1.yaml`、`reviewer.md`、`calibration/ideas.v1.yaml`。评分引擎不改，但 findings schema 增加 `guess` 字段（reviewer 只看 title + 一句话描述时的猜测和依据）；`audit` 不验证猜测是否真实，只要求字段存在。`qualitycheck` 增加 `-title` 和 `-target-label` 两个 flag，默认值保持 Spec 文案；idea 技能传自己的值。rubric 分四个维度：claim（w2）、problem（w2）、advance（w4）、why（w1）。core 项固定为 `claim.standalone`(w2)、`problem.trigger`(w2)、`next.testable`(w3)、`next.bounded`(w1)；headline 改叫「推进就绪度」，0–100，分三档 0–39 / 40–69 / 70–100。`next.testable` 要求最小动作 + 可观察结果 + 证伪条件。其余项（`claim.specific`、`problem.affected`、`why.nonobvious`、`next.kill`）做诊断，不计入 headline。另出独立的「成熟度」诊断（早期/成形/可推进），不进入 headline。校准对的是分诊标签（推进/观察/搁置），不是质量好坏；比较时按「推进 vs 不推进」二分（headline ≥70 记推进，观察/搁置记不推进），三档仍用于报告。`calibration/ideas.v1.yaml` 记录五篇的人工档位，留一篇做留出样本。reviewer 只看标题和一句话描述先猜正文；猜不中即 `claim.standalone` 不合格；`reviewer.md` 定义「猜不中」的标准。
7. **记录流程拆两段，异步评分有明确机制。** 「记一下」同步跑结构闸门并当场修复。文件落盘、记录 writer 会话 ID 后，`idea-writer` 技能用后台子代理启动独立 reviewer（独立会话 ID，且不接收 writer 的对话上下文）；reviewer 完成后把 `docs/quality/ideas/<id>/quality-report.md` 与 `quality-findings.json` 写盘，并通过后台任务通知把报告路径送回对话。独立性是流程约束：`qualitycheck` 只能验证两个 ID 不同，不能证明上下文隔离。后台子代理不可用或 5 分钟未完成时，退回同步评分（仍在独立会话），并标记报告；评分失败时报告标记 `unavailable`，想法已经入库，不回滚。`scripts/new` 建完文件后，如果 `doc-writer-tool`/`mdstandards` 可用就自动跑结构闸门；不可用就打印检查命令，不阻断建文件。评分产物不进受管文档。
8. **插件与仓库接线。** plugin 增加 `idea-writer` 技能，描述改为 Spec + idea；ideas 仓库 CLAUDE.md 和 `scripts/new` 增加调用约定。分发改用下一次版本号，确保 `plugin.json`、release tag 和安装缓存一致；发布前跑 `make check`，并加一条 idea corpus 的 release smoke test。README、架构文档和 SPEC-001 同步更新；SPEC-001 是 Approved，新增行为走 changelog + 重新批准或独立 SPEC-002，不静默改写。

## Open Questions

- `tags` 是否要限制在 README 的词表内？v1 先允许自由标签，只校验类型。
- `status` 是否要在 v1 校验合法流转？当前只校验枚举值，不校验流转。
- 未来是否用 `id` 做跨想法引用（`related: [ID]`）？v1 不做，但 ID 已为它准备好。
- 校准的停止条件：五篇里至少三篇的「推进就绪度」档位和人工分诊标签一致（留出一篇做留出样本）；否则先改 rubric，不写 Go。
- 插件 policy 的 `20*/**/*.md` 是否会在其他按年归档的仓库误匹配？v1 的行为是：只有仓库配置声明 `type: idea` 时才启用 idea globs；其他仓库默认走 spec，不评估 idea globs。宽 glob 是为了让路径形状规则能看见两层/四层路径。

## Success Criteria

- 对 ideas 仓库跑 `mdstandards -phase 1`：合法文件退出 0；对一个坏文件分别注入 ID 格式、重复 ID、非法状态、缺标题、残留模板 HTML 注释、残留 `id: ABCDEFGH` 哨兵、日期与日期目录不一致、年份目录与日期不一致、非法日历日期、两层/四层路径，每条都能被独立规则捕获；`暂无`、`目前说不清，因为……`、空正文的合法文件退出 0。
- `date` 既可以是 YAML 字符串，也可以被 YAML 解析成 `time.Time`；两种都要归一化为 `YYYY-MM-DD`，带时间的 datetime 报 extract error。
- `.mdstandards.json` 损坏、未知 type、未知键都 exit 2，不静默回退。
- 空或纯空白 title 报结构错误。
- `refs.rego`/`status.rego` 只在有效类型为 spec 时生效。
- idea 报告的标题和目标标签不是 Spec 文案。
- MDStandardsKit 自身 `make check` 保持绿；spec 相关测试零改动通过；spec 的 `-dump-corpus` 输出逐字节不变。
- 五篇存量想法跑完 idea rubric，至少三篇的「推进就绪度」档位与人工分诊标签一致（留出一篇做留出样本）；rubric 使用四个 core 项和三档口径（0–39 / 40–69 / 70–100）；成熟度单独输出；reviewer 与 writer 会话不同；每条证据都能在声明章节中逐字找到。
- 「记一下」流程：结构问题在回复前修掉；内容报告在记录完成后交付，不阻塞想法入库。
- `scripts/new` 在工具可用时自动跑结构闸门；不可用时打印检查命令且不阻断建文件。
