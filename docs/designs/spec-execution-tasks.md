# Design: 给 Spec 增加可执行的 tasks.md 与独立 taskscheck

Supersedes: 不取代；延续 maintainer-main-design-20261102-094931.md 的结构闸门 + 内容评分双层思路，新增执行拆解产物。

## Problem Statement

用户在实际执行 Spec 时发现：Spec 有架构、详细设计、NFR、上线计划，却没有“怎么拆、按什么顺序做、哪些步骤互相依赖”。原话：

> 「我认为确定是任务的拆解顺序和依赖，就是一个复杂的任务，如何拆解成多个步骤多个字任务，然后我可以更好地去管理复杂」

现状的失败链：

1. Spec 写清了目标、架构与详细设计，但没有执行单元。
2. 执行者（人或 Agent）必须自己重新推导顺序与依赖。
3. 隐藏依赖在返工时才暴露；并行的工作写同一个文件，互相覆盖。
4. 第 6 章只回答“上线后怎么不炸”，不回答“先写哪一块”。
5. 质量评分卡没有执行计划维度，因此这个缺口不会被现有工具暴露。

## What Makes This Cool

一份**能证明自己仍然属于这篇 Spec、并且并行车道不会相撞**的执行契约：

- `spec_sha256` 把 tasks.md 钉在 spec.md 上。Spec 一改，`tasks.stale_plan` 立刻出现；重新拆解只改 tasks.md，不必把 Spec 打回 `In Review`。
- `writes` 让“同文件不能并行”从口号变成可计算的不变量；工具能算出真实并行车道与关键路径。
- `done_when` + `verify` 拒绝“完成 / works / tested / TBD”，每步都有可证伪的完成标准。
- 免费副产物是一张 plan-shape 报告：关键路径长度、最热文件、覆盖过多 REQ 的任务、没有任务覆盖的 Goal。这是复杂度仪表盘，不参与阻断。

一句话：**a plan that can prove it still belongs to this spec, and that its parallel lanes do not collide.**

## Constraints

- `governed_globs` 已包含 `docs/specs/**/*.md`。tasks.md 放进 Spec 目录后会被 mdstandards 当作受管文档解析，必须带可解析的 frontmatter，否则 phase 1 因 `extract.parse_error` 退出 2。
- 不能用 `depends_on` 关联 spec.md：Spec 处于 `Draft` / `In Review` 时只允许 `Approved` / `Published` 被依赖，会触发 `refs.status_not_dependable`，还会污染零边覆盖断言。
- `mdstandards` 的 0/1/2 退出码、phase/baseline 语义与 `-dump-corpus` 字节稳定是承重墙，本次不改。
- 不新增运行时依赖；Go 标准库 + 已有依赖。写集合冲突先只做字面路径与前缀比较，不引入 glob 交集库。
- v1 覆盖不变量：Goal 硬覆盖，REQ 覆盖只报告。
- 不做调度器、ready-set 引擎、任务状态账本、Web UI，也不在 spec.md 里加第二个“计划”章节。
- 产物随现有 Claude Code 插件分发，不新增 marketplace 或发布渠道。

## Premises

1. 落点是 `docs/specs/SPEC-xxx/tasks.md`，与 `spec.md` 同目录、按目录配对；重新拆解不触发 Spec 回退。
2. 只派生不复制：每个任务有 ID、覆盖的 Goal/REQ、前置任务、写入范围、可证伪的完成标准与验证方式；不得引入新架构或新范围。
3. 顺序用依赖表达：任务图无环；写同一路径的两个任务若之间没有依赖路径，就是并行冲突。
4. 按需产出：单批可完成的小 Spec 仍要留下 tasks.md，但用 `not_applicable: <理由>` 明示，不允许静默缺失；`not_applicable` 存在时跳过任务表、覆盖、依赖与写入检查，但仍校验 frontmatter 与 `spec_sha256`，且不得同时出现任务表。
5. v1 就是硬闸门：ID 唯一、依赖可解、无环、覆盖引用不悬空、每个 Goal 硬覆盖、完成标准与验证非空、`writes` 无冲突、`spec_sha256` 新鲜；违规按 0/1/2 阻断。REQ 覆盖只报告。

## Cross-Model Perspective

独立 Claude 子代理冷读后的关键判断（Codex 未安装，按流程回退）：

- **最酷的版本**：spec-pinned、conflict-aware 的执行契约，而不是更好的任务清单。`spec_sha256` 解决“计划是否还属于这篇 Spec”，`writes` 解决“并行车道是否相撞”，`done_when` + `verify` 解决“完成标准能否证伪”。
- **最兴奋的点**：用户的原话「如何拆解成多个步骤多个字任务，然后我可以更好地去管理复杂」。对象是**管理复杂**，不是文档合规；通过 lint 但不降低认知负担的 tasks.md 只是仪式。
- **挑战的前提**：REQ 全覆盖作为 v1 硬不变量是错的。SPEC-001 有 27 个 REQ（`grep` 实测），首日回填会直接让 `make check` 变红；还会被“一个任务覆盖所有 REQ”钻空子。建议 Goal 硬覆盖、REQ 只报告。
- **落地建议**：独立 `taskscheck`，不并入 mdstandards；理由是 mdstandards 的契约、`-dump-corpus` 稳定性与 baseline 三元组都不适合任务图。
- **未采纳**：第二意见建议的全文哈希收窄为 ID 指纹——v1 保留全文哈希，简单、确定、可复现；出现真实错别字噪声后再收窄。

## Approaches Considered

### Approach A: 独立 taskscheck（选中）

`tasks.md` 与 `spec.md` 同目录；新增 `tools/taskscheck` 独立二进制，和 `qualitycheck` 同一模式。校验 ID 唯一、依赖可解、无环、覆盖引用不悬空、Goal 硬覆盖、完成标准与验证非空、`writes` 冲突、`spec_sha256` 新鲜；REQ 覆盖只报告。通过 `make check`、CI、doc-writer 第 6 步阻断。

- Effort: M　Risk: 低–中
- Pros: 完全不动 mdstandards 的契约；有 qualitycheck 先例；规则可独立演进；失败面清晰。
- Cons: 多一个二进制要构建、发布、算 checksum；CI 多一条命令；phase/baseline 语义需单独定义。
- Reuses: `go.mod`、dispatcher、release 资产模式、现有测试夹具风格。

### Approach B: 并入 mdstandards（否决）

tasks 作为受管文档类型，`extract.go` 解析任务表，`policy/tasks.rego` 校验图不变量，复用 phase/baseline/format。

- Effort: L　Risk: 高
- 否决原因：表格解析与图算法进入承重墙；`BaselineEntry` 的 `(rule, document, target)` 不适配任务 ID；一个 parser bug 会同时打坏 Spec 闸门；也与“v1 只有两条规则”和 D2 冲突。

### Approach C: 复用 qualitycheck（否决）

给 `qualitycheck` 加 `-check-tasks` 结构模式，不新增二进制。

- Effort: S–M　Risk: 中
- 否决原因：`qualitycheck` 的质量评分只诊断，但审计完整性失败会退出 1；把它改成任务结构闸门会污染评分审计器，结构 findings 与 rubric findings schema 也不同。

## Recommended Approach

**Approach A。** 用独立 checker 兑现硬闸门，同时把 mdstandards 的稳定契约隔离在风险之外。

### tasks.md 契约

位置：`docs/specs/SPEC-xxx/tasks.md`，与 `spec.md` 同目录。

frontmatter：

```yaml
---
type: tasks
status: Draft
owner: <owner>
depends_on: []
spec: ./spec.md
spec_sha256: "<spec.md 全文的 sha256>"
updated_at: <YYYY-MM-DD>
---
```

必填字段与约束：

| 字段 | 约束 | 违反时 |
|---|---|---|
| `type` | 必须逐字为 `tasks` | `tasks.invalid_frontmatter` |
| `status` | 非空，取值 `Draft` / `In Progress` / `Done` | `tasks.invalid_frontmatter` |
| `owner` | 非空字符串 | `tasks.invalid_frontmatter` |
| `depends_on` | 必须恰好是空数组 `[]`；任务依赖只写在表里 | `tasks.invalid_frontmatter` |
| `spec` | 非空，且是 tasks.md 所在目录内的相对路径；空、绝对、越界、URL 均非法 | `tasks.invalid_frontmatter` |
| `spec_sha256` | 64 位小写十六进制；模板中用引号包裹，避免全数字哈希被 YAML 解析成数字 | `tasks.invalid_frontmatter` |
| `updated_at` | `YYYY-MM-DD` 且是真实日历日期 | `tasks.invalid_frontmatter` |
| `not_applicable` | 可选；出现时必须是非空字符串，且文件内不得有任务表 | `tasks.invalid_not_applicable` |

- `spec_sha256` 是 spec.md 字节的 sha256；taskscheck 每次运行重算并比对，不一致产出 `tasks.stale_plan`。
- `not_applicable` 存在时：跳过任务表、覆盖、依赖、写入、`uncovered_goal` 与 `spec_sha256` 检查；仍校验 frontmatter 字段与 `spec` 路径。同时出现 `not_applicable` 与任务表时，整份文件拒绝，产出 `tasks.invalid_not_applicable`。没有任务表就没有可过期的计划，因此豁免哈希。
- 缺失 tasks.md 仍是 `tasks.missing_file`，不允许静默跳过。

任务表（列名固定）：

```markdown
| ID | 任务 | 覆盖 | 依赖 | 写入 | 完成标准 | 验证 |
|---|---|---|---|---|---|---|
| T1 | 抽取语料 | G1, REQ-001, REQ-002 | — | extract.go | dump 出三份语料 | go test ./... -run TestDumpCorpus |
| T2 | 路径归一化 | G1, REQ-005 | T1 | normalize.go | 越界路径产出 extract_error | go test ./... -run TestNormalize |
| T3 | Rego 两条规则 | G2, REQ-010 | T1 | policy/refs.rego | phase 1 对缺失目标出 finding | go test ./... -run TestMissingTarget |
```

- **任务表识别**：先跳过 fenced code block（``` 与 ~~~）；只识别围栏外、表头逐字等于 `| ID | 任务 | 覆盖 | 依赖 | 写入 | 完成标准 | 验证 |` 的表格；同文件其他表格忽略。表头下一行必须是分隔行（每列 `---` 或 `:---`）。
- **转义与分列**：按未转义的 `|` 分列；`\|` 反转义为 `|`；单元格两侧空白 trim。缺少列、列数不符、分隔行缺失或数据行列数不符时，整份文件按解析错误处理（exit 2）。
- `覆盖`：逗号分隔的 `G<n>` / `REQ-<三位数字>`；大小写敏感；不支持范围简写，保证解析确定。
- `依赖`：`—` 或逗号分隔的任务 ID；空单元格等价于 `—`。
- `写入`：`—` 或逗号分隔的写入项。每项是仓库相对 POSIX 路径：反斜杠转正斜杠、去掉 `./` 与重复斜杠；拒绝 `..`、绝对路径、含 `://` 的 URL 与空项；重复项去重。以 `/` 结尾的是目录前缀，否则是字面文件路径；大小写敏感。
- **路径归一化**：`taskscheck` 是独立 main 包，无法 import 主包的 `NormalizeRepoPath`。v1 写一个 `normalizeWritePath`：反斜杠转正斜杠、去掉 `./` 与重复斜杠、**保留尾斜杠**、拒绝 `..`/绝对路径/URL/空项。不能直接复用 `path.Clean`，因为它会吃掉目录前缀的尾斜杠。约 25 行，单独测试；不为此抽 shared package（D2）。
- **大小写**：写入路径按字节比较，保证跨平台一致；两个路径仅大小写不同时产出 `tasks.case_collision` warning（macOS APFS 默认不区分大小写），不阻断。
- `完成标准`：先 trim；剥离开头的 Markdown 强调/代码标记（`**`、`*`、`__`、`_`、`` ` ``），再 trim；全空白视为空。循环去除尾部的中英文句号与感叹号（`。` `．` `.` `!` `！`），ASCII 转小写后，整格等于 `完成`、`works`、`tested`、`tbd`、`待补充` 之一即拒绝。`**完成**` 与 `完成!!` 因此同样被拒。
- `验证`：trim 后非空；命令或测试 ID。
- 任务 ID 语法：`T[A-Za-z0-9_-]*`（必须以 `T` 开头）；禁止逗号、空白与 `—`，否则 `依赖`/`覆盖` 分列有歧义。该前缀与 `G<n>`、`REQ-<三位数字>` 命名空间隔离。
- 任务 ID 在文件内唯一；依赖不得自指；任务图无环。

### Spec ID 提取契约

taskscheck 需要从 spec.md 得到 canonical 的 Goal 与 REQ ID 集合：

- **Goal 定义**：只扫描 `### 2.1 目标` 小节（`## 2. 目标与非目标` 之下）。匹配行首的粗体声明：`^\s*(?:[-*]\s+)?\*\*(G\d+)\b`。只在表格、正文或验收清单里出现的 `G1` 不算定义。
- **REQ 定义**：只扫描 `## 4. 详细设计` 及其子小节。匹配行首的粗体声明：`^\s*(?:[-*]\s+)?\*\*(REQ-\d{3})\b`。只在第 6 章验收表里出现的 `REQ-001` 不算定义。
- **集合语义**：大小写敏感、逐字匹配；同一 ID 多次定义只计一次，不报错。ID 之间的顺序不影响结果。
- **空集处理**：没有 Goal → exit 2（`spec.no_goals`，fail closed，因为没有可硬覆盖的合约）；没有 REQ → 跳过 REQ 覆盖报告，不产出 warning，Goal 覆盖照常。
- **实现方式**：逐行扫描，只用正则，不引入 Markdown AST 依赖。SPEC-001 的 `**G1 引用存在**` 与 `**REQ-001**` 是基准夹具；另加无 Goal、无 REQ 两个夹具。

### 写入冲突判定

对两个不同任务 `Ta`、`Tb`，若存在写入项 `wa ∈ Ta.writes`、`wb ∈ Tb.writes` 满足以下任一条件，则构成候选冲突：

- `wa == wb`；或
- 其中一个是目录前缀，且另一个位于其下（目录项以 `/` 结尾；`a/` 是 `a/b.go` 的前缀，字面文件 `a` 不是 `a/b` 的前缀）。

候选冲突只有在 `Ta` 与 `Tb` 之间**双向都不存在有向依赖路径**（传递可达，不是只看直接边）时才产出 `tasks.write_conflict`。同一任务内的重复写入先去重，永不构成冲突。夹具覆盖：同字面路径、目录前缀、有依赖关系的同路径（允许）、无依赖关系的同路径（阻断）。

实现用一次遍历建立 `path -> tasks` 映射，并为每个写入项检查其目录祖先；再用一次 bitset 传递闭包回答双向可达（1000 任务约 125 KB），避免每个候选对做 DFS。总复杂度 O(总写入数 × 路径深度 + V²/64)；1000 任务、冲突密集夹具一起进基准。

### 规则清单

| 规则 ID | 触发 | 结果 |
|---|---|---|
| `tasks.parse_error` | 文件不可读、无 frontmatter、YAML 非法、任务表无法分列 | exit 2 |
| `tasks.no_specs` | 发现 0 个 `spec.md` | exit 2 |
| `tasks.invalid_spec_flag` | `-spec` 为空条目、越界、不存在、非 `spec.md` | exit 2 |
| `tasks.usage` | flag/format 错误或缺必填参数 | exit 2 |
| `spec.no_goals` | Spec 没有可硬覆盖的 Goal | exit 2 |
| `tasks.missing_file` | 状态为 `Approved` / `Implemented` 的 spec 没有 tasks.md | exit 1 |
| `tasks.orphan_tasks` | tasks.md 没有同目录的 spec.md | exit 1 |
| `tasks.invalid_frontmatter` | frontmatter 可解析，但缺必填字段或取值非法 | exit 1 |
| `tasks.invalid_task_id` | 任务 ID 不匹配 `T[A-Za-z0-9_-]*` | exit 1 |
| `tasks.invalid_write_path` | 写入路径为空、绝对、URL 或含 `..` | exit 1 |
| `tasks.missing_spec` | `spec` 解析后的目标不存在；不再继续覆盖检查 | exit 1 |
| `tasks.wrong_spec_path` | `spec` 指向的文件存在，但未解析到同目录的 `spec.md` | exit 1 |
| `tasks.stale_plan` | `spec_sha256` 与当前 spec.md 不一致；消息同时给出 expected 与 got | exit 1 |
| `tasks.duplicate_id` | 任务 ID 重复 | exit 1 |
| `tasks.unknown_dependency` | 依赖指向不存在的任务 ID | exit 1 |
| `tasks.self_dependency` | 依赖自己 | exit 1 |
| `tasks.dependency_cycle` | 任务图有环 | exit 1 |
| `tasks.unknown_coverage` | 覆盖了 Spec 中不存在的 ID | exit 1 |
| `tasks.empty_coverage` | 某任务没有覆盖任何 ID | exit 1 |
| `tasks.goal_not_dedicated` | 某个 Goal 没有专用任务（`覆盖` 含该 Goal、且不含其它 Goal；可含 REQ） | exit 1 |
| `tasks.empty_done_criterion` | 完成标准为空 | exit 1 |
| `tasks.banned_done_criterion` | 完成标准是禁用词或泛化短语 | exit 1 |
| `tasks.empty_verify` | 验证为空 | exit 1 |
| `tasks.verify_not_executable` | 验证不是命令、测试 ID 或产物路径 | exit 1 |
| `tasks.write_conflict` | 两个无依赖路径的任务写入同一路径/前缀 | exit 1 |
| `tasks.case_collision` | 两个写入路径仅大小写不同（macOS APFS 风险） | warning |
| `tasks.uncovered_requirement` | 某个 REQ 没有任务覆盖 | warning |
| `tasks.invalid_not_applicable` | `not_applicable` 为空，或与任务表同时存在 | exit 1 |

`spec` 字段的校验顺序是互斥的，不允许两条规则同时命中：

1. 把 `spec` 按 tasks.md 所在目录解析并规范化。路径非法（空、绝对、越界、URL）→ `tasks.invalid_frontmatter`（exit 1）。
2. 目标文件不存在 → `tasks.missing_spec`（exit 1），**不再**检查是否为同目录 `spec.md`，也不再做覆盖检查。
3. 目标存在，但规范化后不等于同目录的 `spec.md` → `tasks.wrong_spec_path`（exit 1）。
4. 目标存在且等于同目录 `spec.md` → 通过，继续做哈希校验。

夹具：`spec: ./nope.md` 必须得到 `tasks.missing_spec` 与 exit 1，且不产出 `tasks.wrong_spec_path`。

退出码与错误分类：

- **exit 2（工具/解析错误）**：`tasks.parse_error`、`tasks.no_specs`、`tasks.invalid_spec_flag`、`tasks.usage`、`spec.no_goals`。这些是 checker 无法完成工作的状态，任何时候都不被 `-phase 0` 放过。
- **exit 1（阻断 finding）**：validly parsed 之后的规则违规，包括 `tasks.missing_spec`。`-phase 1` 阻断。
- **exit 0**：没有 exit 1 的 finding；`-phase 0` 下即使有 finding 也退出 0，但必须完整输出 findings，作为存量迁移的过渡。
- **phase**：v1 只接受 `0` 与 `1`；`-phase 2` 作为 usage error 退出 2（没有 baseline，phase 2 没有独立语义）。
- **baseline**：v1 不提供。迁移路径是 `-phase 0` 观察，回填后切 `-phase 1`；若未来需要按 `(rule, spec, task)` 抑制存量，再单独设计，不复用 mdstandards 的三元组。

### 计划形状报告（不阻断）

table/json 输出附带，**不参与退出码**：

- `critical_path`：最长依赖链的任务 ID 数组与长度；
- `parallel_groups`：按依赖层级分组的可并行任务 ID 数组；
- `hot_paths`：被最多任务写入的路径及计数；
- `over_covered_tasks`：覆盖超过 5 个 REQ 的任务；v1 固定阈值 5，不加 flag；
- `uncovered_requirements`：没有任务覆盖的 REQ 列表（与 warning 同源）。

table 按以上顺序逐段打印；JSON 放在 `plan_shape` 对象里；`-format github` 只为 findings 与 errors 输出注解，计划形状报告写一行 `::notice::` 摘要。

排序稳定性：`critical_path` 并列时取字典序最小的任务 ID 序列；`parallel_groups` 组内按 ID 排序、组间按深度再按首 ID；`hot_paths` 按计数降序再按路径升序；`over_covered_tasks` 按计数降序再按任务 ID；`uncovered_requirements` 按 ID 升序。

### CLI 契约

```text
taskscheck [flags]
  -root .      仓库根；只决定发现范围
  -spec ""     逗号分隔的 spec.md 路径；为空时在 root 下发现 docs/specs/**/spec.md
  -phase 1     0 只报告、1 阻断、2 阻断（v1 与 1 相同，无 baseline）
  -format table   table|json|github
  -out ""      把报告写入文件而不是 stdout
  -version     打印版本并退出
  -print-spec-hash ""  打印 spec.md 的 sha256 并退出，用于写回 tasks.md
```

- 未给 `-spec`：发现 `docs/specs/**/spec.md`，排除 `docs/specs/archive/`，逐个配对同目录的 `tasks.md`。发现数为 0 → exit 2（覆盖断言，不允许静默通过）。
- 生命周期：读 spec.md 的 `status`。`Approved` / `Implemented` 必须有 tasks.md，缺失产出 `tasks.missing_file`；`Draft` / `In Review` / 缺失 status 可选，存在就检查，缺失不报错。另发现 `docs/specs/**/tasks.md`，没有同目录 spec.md → `tasks.orphan_tasks`。
- 给了 `-spec`：路径按**当前工作目录**解析（与 `-policy` 一致），规范化后必须位于 `-root` 内，否则 exit 2。空条目、不存在的文件、目录，或文件名不是 `spec.md` 的路径，都是 exit 2。tasks.md 固定取该 spec 的同目录。
- 多个 spec 的 findings 聚合后按 `(spec, rule, task)` 排序，保证字节稳定。
- 多个 spec 中任一触发 exit 2 时，继续检查其余 spec，输出全部 findings 与 errors，最终整体 exit 2；不短路丢弃其他 spec 的结果。
- `-phase 0` 只改变退出码，不改变报告内容；`-phase 2` 在 v1 等同 `-phase 1`，保留给未来 baseline。
- `schema_version` 固定为 `"1"`。
- JSON 形状：`{schema_version, findings:[{rule, spec, task, message, severity}], errors:[{rule, spec, task, message}], stats:{specs_checked, tasks_checked, warnings, errors}, plan_shape:{critical_path, parallel_groups, hot_paths, over_covered_tasks, uncovered_requirements}}`。
- `severity` 取值只有 `error` 与 `warning`。exit 2 的 `tasks.parse_error`、`tasks.missing_spec`、`spec.no_goals` 进入 `errors` 数组，不进入 `findings`；`stats.errors` 是它们的计数。
- `spec.no_goals` 是 checker 级错误，规则清单中标注为 exit 2。
