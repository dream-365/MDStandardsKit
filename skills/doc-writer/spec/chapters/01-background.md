# 第 1 章：背景与上下文

目标：让评审者在不看方案的情况下，判断"这个方案是否必要"。

## 四个维度

1. **系统现状**：相关模块或服务现在负责什么，核心流程怎么走。
2. **技术痛点**：性能/扩展性、代码/架构质量、可运维性、工程效率。要写失败链。
3. **触发点**：业务驱动（流量、合规、新形态）或技术驱动（上游废弃、基础设施升级、技术栈演进）。
4. **约束与非目标**：是否零停机、是否向后兼容、哪些明确不在本次范围。

## 模板

```markdown
## 1. 背景与上下文

### 1.1 系统现状
[服务/模块] 目前负责 [核心职责]。当前采用 [架构/技术栈]，核心流程如下：
* 数据/请求从 [A] 进入，经由 [B] 处理，落到 [C]。

### 1.2 核心技术痛点
随着 [业务量/架构演进]，现有设计暴露：
1. **[性能/扩展性]**：当 QPS 超过 X，DB 连接池打满，P99 升到 Y ms。
2. **[耦合/可维护性]**：[业务 A] 与 [存储/通信] 强绑定，新增 [功能] 要改多处。
3. **[可观测性/稳定性]**：缺少 [追踪/日志/Checkpoint]，故障时无法定位失败节点。

### 1.3 重构/设计动机
为了支持 [目标]，本次方案旨在：
* 解耦 [A] 与 [B]，抽象统一 [接口/领域模型]。
* 将 [核心指标] 提升至 [目标值]。

### 1.4 非目标
* 本方案**不涉及** [下游服务改造]。
* 本方案**暂不考虑** [多机房多活]，留待后续阶段。
```

## 好与差

差：`现有服务太慢、代码很乱、扩展性不好，所以决定重构。`

好：`DocParser 把下载、版面分析、清洗、存储交织在一个 Service 里，同步阻塞。新增 EPUB/Markdown 要改核心流程；大文件解析内存飙升，崩溃后整个 Batch 重跑；缺少 OpenTelemetry，提取错误无法定位到段落。`

## 检查

- 1.1 有现状和核心流程，不是一句"现有系统"。
- 1.2 有失败链和至少一条证据（事故、度量、引述）。
- 1.3 有触发点，解释为什么现在做。
- 1.4 写清不做的后果和本次非目标。
