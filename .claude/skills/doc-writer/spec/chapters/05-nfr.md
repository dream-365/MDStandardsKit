# 第 5 章：非功能性需求

目标：定义系统"能不能稳定、高效、安全地长期运行"。每条都必须可度量。

## 四个维度

1. **性能与资源**：P95/P99 延迟、QPS/并发、CPU/内存/磁盘/连接池峰值。
2. **高可用与容灾**：SLA、依赖超时/挂掉时的降级、RTO/RPO。
3. **可观测性**：结构化日志、Trace ID、Prometheus 指标与告警阈值。
4. **安全、隐私与合规**：传输/静态加密、JWT/API Key/OAuth、权限校验。

## 模板

```markdown
## 5. 非功能性需求

### 5.1 性能与吞吐
* **延迟**：标准 10 页 PDF 首字响应 < 500ms。
* **并发**：单节点 ≥ 20 个并发解析任务，不阻塞事件循环。
* **资源**：流式分块，单任务内存峰值 < 500MB。

### 5.2 可靠性与容灾
* **断点恢复**：进程被 Kill 后从最近 Checkpoint 恢复，数据丢失率 0。
* **幂等性**：相同 `Task ID` 重复提交不产生脏数据。

### 5.3 可观测性
* **链路追踪**：全流程 OpenTelemetry，关键算子独立 Span。
* **结构化日志**：禁止 Print，记录 `task_id`、`user_id`、`error_code`。

### 5.4 安全与合规
* **文件隔离**：临时文件沙箱，任务完成 24 小时内擦除。
* **输入校验**：MIME 嗅探 + 大小校验（最大 50MB）。
```

## 避坑

- "系统要安全、快速、稳定"不是 NFR。必须可测试、可度量。
- 指标要结合真实环境：单台 2C4G 容器、云端 SQLite/MongoDB 的性能上限。
- 未实测的指标标 `[estimated]`，不要写成已达成。

## 检查

- 每条 NFR 有数字、单位或明确的验收方式。
- 覆盖性能、可靠性、可观测性、安全四类，或说明哪类不适用。
- 未实现的项标 `未实现`，不假装通过。
