# 第 7 章：替代方案与权衡

目标：提前回答"为什么不用 X 而选 Y"，把评审会上最容易吵的问题先摆平。

## 结构

1. **Status Quo（什么都不做）**：维持现状的成本、风险、何时达到阈值。
2. **被否决方案 1..N**：核心思路、优点、淘汰原因（对着当前约束，不是拉踩）。
3. **最终选型与权衡矩阵**：成本、性能、复杂度、契合当前阶段。

每个方案都有适用场景；重点写"为什么不适合我们当前的约束"，不是"它很烂"。

## 模板

```markdown
## 7. 替代方案与权衡

针对 [核心痛点/存储选型/并发调度]，评估了三种方案，最终选择 **方案 C**。

### 7.1 方案 A：Redis + Celery 分布式队列
* **思路**：外部 Redis 分发，Celery Worker 池化。
* **优点**：生态成熟，天然横向扩展。
* **淘汰**：团队规模小，运维与高可用成本高；不满足单机开箱即用。

### 7.2 方案 B：多进程同步解析
* **思路**：本地 multiprocessing 分块。
* **优点**：实现简单，无额外状态机。
* **淘汰**：不支持流式与断点恢复；CPU 密集阻塞事件循环。

### 7.3 方案 C：异步管线 + SQLite Checkpoint（当前选型）
* **理由**：无额外中间件，支持节点级恢复与流式推送。

| 维度 | A | B | C |
| --- | --- | --- | --- |
| 开发与运维成本 | 高 | 低 | 中 |
| 高可用与容灾 | 强 | 差 | 强 |
| 流式支持 | 较弱 | 弱 | 强 |
| 契合当前阶段 | 否 | 否 | **是** |
```

## 避坑

- 不要把备选方案写成一无是处；评审者会怀疑你没认真评估。
- 不要漏掉 Status Quo；最大的竞争对手常常是"维持现状"。
- 权衡矩阵的维度要和约束对应，不要堆无关指标。

## 检查

- 有 Status Quo。
- 至少一个被否决方案，且淘汰原因对应当前约束。
- 有权衡矩阵。
- 结论与第 2 章的 Goals、第 3 章的选型一致。
